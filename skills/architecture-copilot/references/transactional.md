# 参考库 · 交易与一致性类

覆盖模板:`ecommerce-platform` `payment-system` `online-ticketing` `notification-system` `ride-hailing`

---

### 电商平台:高并发交易与库存一致性 (`ecommerce-platform`)
**关键决策**
- 库存扣减:悲观锁(绝对防超卖但锁竞争瓶颈) vs 乐观锁(高吞吐但热点冲突率极高)——普通商品用乐观锁,热点 / 秒杀上「预扣 + 分段 + 排队」组合。
- 订单支付一致性:分布式事务(锁资源久、吞吐极低) vs Saga + 对账(拆成可补偿步骤,但须自建对账系统)——几乎必选 Saga。
- 洪峰:硬扛(成本高、DB 无法无限扩) vs 整形(削峰限流降级预热,但体验有损)——要整形不硬扛。
- 幂等:涉及钱和库存的写必须幂等,无例外;订单必须用状态机保证可审计。

**常见反模式**
- 用大事务串「扣库存→建单→支付→发货」(应拆可补偿 Saga)。
- 下单同步等支付回话堵死链路;库存硬扣 `库存=库存-1` 不防超卖;信任客户端价格 / 库存 / 优惠;用最终一致却不建对账。

**演进与触发信号**
- MVP:单体一应用一库,验证生意跑不跑得通。成长(万~百万单):拆库存 / 订单 / 支付核心域、加缓存 / 专用搜索 / 读写分离。成熟(千万级 + 大促):分段库存、异步下单削峰、限流降级、对账系统、多活容灾。升级信号:热点库存争抢、大促洪峰、海量读压力、对账压力出现即升级。

### 支付系统:资金安全与账务正确性优先 (`payment-system`)
**关键决策**
- 账户余额:直接改字段(简单但难审计) vs 复式记账(账天然守恒、可审计、不可篡改)——正经支付必用复式记账。
- 超时处理:直接判失败(钱可能凭空消失) vs 引入「未知」状态 + 查询补偿 + 对账兜底——必须区分失败与未知。
- 一致性分层:资金核心强一致 vs 周边事件驱动最终一致,兼顾性能与正确性。
- 幂等:每请求带唯一幂等键 + 唯一约束,必做无例外。

**常见反模式**
- 用「读-改-写」更新账户(应复式记账 + 不可变分录)。
- 信任外部回调(应验签 + 以己方查询为准)、超时直接判失败、卡号明文存储 / 打日志(应令牌化不落地)、为性能牺牲正确性。

**演进与触发信号**
- MVP:接第三方支付薄封装,合规安全外包。成长(多渠道):自建编排 / 账本 / 对账 / 风控,把「幂等、对账、未知态」做扎实。成熟(平台级):清结算、多币种、监管报送、容灾。升级信号:热点账户写争抢→子账户拆分;对账数据爆炸→分库分表 + 离线批处理;渠道限流抖动→多渠道路由自动切换(注意资金核心须顺账户边界切,不能无脑分片)。

### 在线抢票:瞬时洪峰与防超卖公平 (`online-ticketing`)
**关键决策**
- 削峰:所有人直打核心 vs 虚拟等候室按承载力分批放行——「把洪峰挡在门外远比门内加机器有效」。
- 库存扣减:DB 读改写(必超卖) vs 行锁 / 乐观锁(扛不住热点) vs 内存原子操作(最优)——并发不大用行锁,热门场次用内存原子扣减。
- 座位:锁定 + 超时自动释放,防占座不付永久占票。
- 流程:抢资格(扣库存)做成同步极快原子,后续流程异步化。

**常见反模式**
- 所有人直接打核心系统(应虚拟等候室削峰)。
- 非原子「查-减-写」(应原子操作 / 行锁);锁座不设超时;热点库存硬塞普通 DB;不防机器人(应风控 + 实名 + 限购守公平)。

**演进与触发信号**
- MVP(小型活动):DB 行锁 / 乐观锁,先保不超卖。成长(中等抢购):内存原子扣减 + 锁座超时 + 限购。成熟(大麦 / 12306 级):虚拟等候室 + 分段库存 + 多级缓存。升级信号:开售峰值→等候室 + CDN;热点库存竞争→内存扣减 + 分段;查余票读放大→多级缓存(容忍秒级延迟);排队系统压力→极简化 + 水平扩展。

### 通知系统:异步大扇出与不打扰 (`notification-system`)
**关键决策**
- 发送方式:同步(阻塞业务、渠道延迟拖累主流程) vs 异步——必须异步,发通知是非关键路径绝不阻塞业务。
- 投递保证:at-least-once 重试(可能重复) + 客户端幂等去重——「宁重勿丢,靠幂等兜重复」。
- 推送渠道:自建 vs 用平台——App 推送一律经 APNs / FCM,系统只负责调好平台。
- 去重限频:必做,「不打扰」是产品生命线,含幂等去重、限频、聚合。

**常见反模式**
- 同步发通知阻塞业务(应异步队列)。
- 无去重限频轰炸(应去重 + 限频 + 聚合摘要)、交易和营销混优先级(应分优先级分通道)、忽视用户偏好硬发、逐条发送无批量、假设渠道必成功。

**演进与触发信号**
- MVP:1-2 渠道 + 简单异步队列。成长:多渠道 + 模板 + 偏好 + 去重限频。成熟:优先级队列、智能聚合、跨渠道编排、可观测。升级信号:营销扇出洪峰→队列削峰 + 批量分片;渠道限流→配额排队平滑发送;重要通知被挤压→交易 / 安全类走高优先级独立通道;投递状态数据海量→时序存储 + 聚合统计。

### 网约车:实时地理位置与供需撮合 (`ride-hailing`)
**关键决策**
- 附近车查询:DB 用 WHERE 算距离 vs 空间索引(GeoHash / 网格)——必用空间索引,把二维邻近映射为可索引结构。
- 位置数据:全部强一致落库 vs 实时位置放内存、轨迹采样异步落库——「别为不需持久化的易失数据付出持久化代价」。
- 匹配:就近贪心(简单) vs 批量撮合(整体效率高但单次延迟增加)——初期贪心,规模后批量。
- 高峰:只加机器硬扛 vs 动态溢价「用经济杠杆做流量调节」(抑需求 + 引供给);按地域天然边界分片。

**常见反模式**
- 用数据库 WHERE 算距离(应空间索引)。
- 每条位置强一致落库(应内存 + 异步采样)、全局一个大池子撮合(应按区域分片)、高峰只加机器硬扛(应排队 + 动态定价削峰)、把位置当普通数据(须认清其易失高频只活几秒本质)。

**演进与触发信号**
- MVP(单城市):内存索引 + 就近匹配 + 行程库。成长(多城市):地域分片、动态定价、ETA 优化、长连接层。成熟(全球):批量全局撮合、ML ETA / 定价、拼车、运力预测。升级信号:位置写入洪峰→内存索引 + 地域分片;局部供需爆炸→区域隔离 + 排队 + 定价削峰;海量长连接→接入层水平扩展 + 区域就近部署。
