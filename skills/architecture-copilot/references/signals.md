# 何时该升级架构:量化触发信号对照清单

> 数字是「经验数量级」不是铁律,真实阈值取决于硬件、数据形态、业务容忍度。真正的依据永远是:某个你在乎的质量属性,被真实瓶颈卡住且你量出来了。

## 数据层(读 / 写 / 存储)
- 主库 CPU 持续 > 70%、读请求排队 → 读打满:加**读副本**(复制扩读) + 缓存。
- 缓存命中率掉到 < 90%、回源压力大 → 缓存不够 / 失效策略差:调粒度、TTL、预热,防穿透击穿雪崩。
- 单表行数过千万~上亿,或单库容量过几百 GB → 单库装不下 / 写变慢:考虑**分片**扩写,慎选分片键。
- 写 QPS 接近单库上限、主库成写瓶颈 → 写打满(复制救不了):分片,或拆独立写服务。
- 同一份数据被多种查询形态折磨(要事务又要全文又要聚合) → 一种存储扛了不该扛的活:按访问形态拆存储(多语言持久化)。

## 性能 / 延迟层(体验)
- P99 延迟持续超标而 P50 尚好 → 尾延迟:找最慢那一跳针对性优化,别动 P50。
- 某耗时操作让用户干等 > 几秒 → 同步阻塞:异步化 + 队列削峰。
- 流量出现规律性尖峰(开售 / 大促 / 早晚高峰) → 按峰值堆机器太贵、按均值被冲垮:削峰填谷 + 弹性扩缩 +(极端)排队。

## 可靠性层(可用性)
- 业务要求可用性上一个台阶(99%→99.9%→99.99%) → 单点 / 无冗余撑不住:消灭单点、加冗余、故障域隔离、多活。
- 某组件一挂全系统瘫(SPOF) → 单点故障:冗余 + 自动故障转移。
- 一次故障波及面过大、恢复慢 → 故障域没隔离:隔离爆炸半径、限流降级、熔断。

## 组织 / 研发效率层(最易被忽视)
- 改一处牵动一片、发布越来越慢、谁都不敢动 → 模块边界烂 / 耦合过紧:先理清边界(模块化单体),未必要拆服务。
- 多团队在一个代码库里互相阻塞、上线排队 → 「人」的扩展性到顶:这才是微服务的真正信号,但先看团队边界(康威定律)。
- 新人上手要好几周、改功能要动很多地方 → 可维护性差:重构边界、补文档 / ADR,而非堆新功能。

## AI 层(LLM / RAG / Agent 专属)— 编者补充,非上游原文
> 以下综合自各 AI 模板的演进信号(见 ai-native.md),不在上游《演进触发信号》中,仅供 AI 系统参考。
- GPU 打满致首字延迟飙升、单 token 成本压不下去 → 上连续批处理、prompt / KV 缓存、模型路由。
- 上下文频繁撞窗口、压缩后丢关键信息 → 上 RAG / 外置记忆 / 分层上下文管理。
- 召回 / 准确率不足、检索质量瓶颈 → 混合检索 + 重排、语义切块、上下文增强。
- eval 指标退化、人审积压、工具误操作增多 → 加评测门禁、human-in-the-loop、权限沙箱收紧。

## 使用原则
先量再判断;一次只解一个瓶颈;每次升级都写一条 ADR(什么信号触发、升成什么、放弃了什么);没触发就别动——升级是「被真实信号触发、有据可查的决策」,不是定期重构的仪式,也不是追新的冲动。
