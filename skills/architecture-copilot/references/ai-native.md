### 面向终端用户的 AI 对话产品 (`ai-chat-product`)
**关键决策**
- 流式 SSE vs 一次性返回:必选流式,首字 1 秒内出(代价:连接管理、重试恢复更复杂)。
- 连续批处理 vs 单请求算:必批处理拉满 GPU(代价:调度复杂、抬高尾延迟)。
- 缓存提示前缀 vs 每轮重算:规模化后必做 KV / prompt 缓存(代价:显存占用、失效策略复杂)。
- 长上下文 vs RAG:资料一多用 RAG(代价:维护切块检索管线)。
- 大模型通吃 vs 模型路由:规模化后按难度分流(代价:路由逻辑)。
- 会话状态放服务端 vs 客户端:客户端带历史起步简单(每轮传输变大),规模化后服务端存会话 + 只传增量(需会话存储与一致性)。

**常见反模式**
- 当普通 CRUD 设计、忽视 GPU 是稀缺资源(一切先问对成本 / 利用率意味什么);不做流式憋完整答案(首字延迟是第一体验指标);每轮全量重喂历史从不缓存(丢掉最大省钱点);直接信任工具 / 检索文本(当不可信输入防注入);同步工具调用阻塞流式(工具应异步、别卡住首字);不记 token 账(既超窗口又爆账单)。

**演进与触发信号**
- MVP:直调供应商 API + 薄编排层,客户端带历史,简单 SSE,无 RAG / 无自建 GPU。成长:引入会话存储、RAG、审核、限流配额、prompt 缓存;自建则上连续批处理。成熟:多区域 GPU 集群、模型路由、精细显存管理、Agent 工具生态、评测 / 可观测、多租户隔离。升级信号:GPU 打满致首字延迟飙升、单请求显存吃紧致并发下降、P99 尾延迟恶化、单 token 成本压不下去(成本不优化则毛利为负)。

### 统一多模型接入的 LLM 网关 (`ai-gateway`)
**关键决策**
- 缓冲 vs 流式透传:必须透传,网关是透明管道(代价:连接管理、中途错误恢复复杂)。
- 托管(OpenRouter / Cloudflare) vs 自部署(One API / LiteLLM):个人起步用托管;团队 / 平台级自部署做高可用(代价:自运维)。
- 精确缓存 vs 语义缓存:默认精确;语义缓存命中率高更省钱但有答非所问风险,仅高容忍场景配阈值开。
- 负载均衡策略:健康度优先 + 故障转移链打底,叠价格 / 延迟权重,核心是别把流量全压一家。

**常见反模式**
- 缓冲完整响应再返回(应流式透传);把网关做成有状态难扩单点(应无状态 + 水平扩 + 状态外置);不解析 token 不计量(成本失控、出不了账单);滥用语义缓存致答非所问;上游 key 暴露 / 打进日志(应网关独占托管、脱敏);只接一家上游它挂全挂(应多上游 + 故障转移链)。

**演进与触发信号**
- MVP / 个人:直接用托管或单机起 One API / LiteLLM,接 1–2 上游,先跑通「统一接口 + 看到花多少钱」。成长 / 团队:自部署配多供应商路由 + 故障转移、按团队配额限流、内存级缓存、关系库存用量。成熟 / 平台:网关多副本高可用 + 集中限流、接专业可观测(Helicone)、精细计费与多租户隔离、按需开语义缓存与护栏。升级信号:关注容错、配额、缓存命中率、精确计费、合规与滥用治理。

### 可溯源的 RAG 知识库 (`rag-knowledge-base`)
**关键决策**
- RAG vs 长上下文 vs 微调:资料多 / 常更新 / 要溯源选 RAG;极少且固定用长上下文;改行为风格而非知识用微调。
- 固定大小切块 vs 语义 / 结构切块:从「固定大小 + 重叠」起步,质量不够上语义切(切块是最被低估却最影响效果的环节)。
- 纯向量 vs 混合检索:生产级用混合(向量 + BM25) + 重排,尤其对专有名词 / 精确关键词(代价:维护两套索引)。
- 是否给块补充上下文:对召回敏感场景做上下文增强(参见 Contextual Retrieval)。

**常见反模式**
- 检索差却怪模型笨(RAG 上限 = 检索上限,先优化检索);切块拍脑袋(太大 / 太小 / 无重叠);只用向量检索(应混合检索 + 重排);把检索内容当可信(当不可信输入防注入);不给引用(可溯源才可信);能用长上下文 / 微调却硬上 RAG。

**演进与触发信号**
- MVP:现成框架(LlamaIndex / Dify / RAGFlow),固定切块 + 纯向量,先跑通问答链路。成长:混合检索 + 重排、语义切块、引用溯源、权限过滤,建立检索质量评测。成熟:上下文增强检索、向量库分片、检索质量持续评测、Agentic RAG(多轮检索)。升级信号:召回 / 准确率不足、成本上升、多租户与海量规模需求出现即升级。

### 语义检索的向量数据库 (`vector-database`)
**关键决策**
- 精确最近邻 vs 近似 ANN:几乎必选 ANN,用精度换速度,召回率可调可接受。
- 索引类型:HNSW 查询快召回高但占内存(中小规模首选);IVF 省内存需训练召回略低(大规模);DiskANN 放磁盘(单机内存放不下)。
- 召回率 vs 延迟 / 内存:无最优解,按业务压测调参(如 HNSW 的 ef、M)。
- 专用向量库 vs pgvector:小规模且已有 Postgres 先用 pgvector(百万级够);规模大 / 要分布式上 Milvus / Qdrant / Weaviate。

**常见反模式**
- 追求精确最近邻(应用 ANN 接受可控近似);不管内存盲目上 HNSW(大规模考虑 IVF / DiskANN / 量化);只看延迟不看召回;几万条也上重型专用库(pgvector / 单机 FAISS 够,别过度设计);以为「向量相似」即「业务相关」(按业务评测,必要时加重排)。

**演进与触发信号**
- MVP(<百万):直接 pgvector 或单机 FAISS,用 HNSW,别引入新系统。成长(百万~亿):上专用向量库,HNSW + 分片 + 副本、带过滤检索。成熟(十亿 +):分布式、量化 / DiskANN 降内存、冷热分层、与全文检索融合。升级信号:内存吃紧、向量量超单机、写入 / 索引重建开销大、带过滤检索效率低即升级。

### 高吞吐 LLM 推理服务 (`inference-serving`)
**关键决策**
- 静态批处理 vs 连续批处理:必选连续批处理,避免短请求被长请求拖等(代价:调度复杂,但吞吐提升数量级)。
- KV 缓存连续分配 vs 分页:选 PagedAttention 分页,消除显存碎片、支持更高并发。
- 吞吐 vs 延迟:离线偏大 batch 求吞吐、在线偏小 batch 求延迟,高级做法 prefill / decode 分离调度。
- 自建推理 vs 直调 API:先调 API(经网关),等量大到自建更划算或必须私有 / 定制模型时再自建。

**常见反模式**
- 用静态批处理(应连续批处理别让 GPU 陪等);KV 缓存连续大块分配(应分页管理消除碎片);每请求单独跑(batch=1,GPU 严重空转);盲目追求超大 batch(损尾延迟);MVP 就自建 GPU 集群(应先调 API,量到了再自建)。

**演进与触发信号**
- MVP:别自建,直调供应商 API(经网关);非要私有模型时单卡起 vLLM / TGI 一实例。成长:自部署 vLLM / SGLang,开连续批处理 + 分页 KV + 前缀缓存,量化省显存,多副本 + 负载均衡。成熟:多卡并行跑大模型、prefill / decode 分离、多区域 GPU 池、模型路由、自动扩缩容。升级信号:单卡吞吐 / 单 token 成本待压优、并发与容量增长、需容灾与质量-延迟平衡时升级。

### 任务自动化的 AI Agent 平台 (`ai-agent-platform`)
**关键决策**
- 确定性工作流 vs 自主 Agent:默认工作流(可预测、便宜、好调试),仅任务确实开放需随机应变才上自主 Agent(「能不用 Agent 就别用」)。
- 循环兜底:必须设多重上限(最大步数 / 成本 / 超时 / 重复检测),自主性越高越要硬刹车。
- 工具执行安全边界:一律沙箱 + 最小权限,不可逆 / 高影响操作走 human-in-the-loop 审批。
- 单 Agent vs 多 Agent:从单 Agent 起步,复杂到一角色扛不动再拆(规划者 + 执行者 + 审查者,代价:协调 / 成本 / 延迟上升)。

**常见反模式**
- 能用固定流程却硬上自主 Agent(简单任务用工作流,可预测又便宜);循环不设上限;给 Agent 无限制工具权限(应最小权限 + 沙箱 + 高危人工确认);信任工具 / 检索返回内容(当不可信输入防注入);不做可观测多步全黑盒(全程 trace 否则无法调试)。

**演进与触发信号**
- MVP:用 Dify / Coze 拖拽搭固定工作流或单 Agent + 几个工具,设好步数 / 成本上限,先验证自动化靠不靠谱。成长:用 LangGraph 等自定义编排,加长期记忆、human-in-the-loop、状态持久化、trace 可观测。成熟:多 Agent 协作、durable 长任务、精细权限与沙箱、模型路由控成本、持续评测成功率。升级信号:成功率 / 可控性不足、成本失控、需人审与可调试、任务复杂度与价值上升时升级。
