# 参考库 · Web 与产品类

覆盖模板:`standard-web-app` `mobile-app` `browser-extension` `url-shortener` `search-engine` `social-feed`

---

### 标准 Web 应用:单体优先的通用后端 (`standard-web-app`)
**关键决策**
- SSR vs CSR:内容型(SEO / 首屏)选 SSR;弱交互场景别硬上重型前端(用复杂度换你不需要的东西)。
- 单体 vs 微服务:几乎永远先单体;微服务解决「组织规模」而非「技术先进」,过早拆分只承受分布式全部苦难却享不到好处。
- 加缓存时机:无读压力就加缓存 = 净亏(只付一致性复杂度);读多写少且库吃力才加。
- 有状态 vs 无状态:应用层必须无状态(状态外置),否则会话黏连、扩不动——少数「第一天就该守」的纪律。

**常见反模式**
- 一上来上微服务(应为组织规模准备,非炫技)。
- 应用层有状态、过早分库分表、N+1 循环查库(最高频杀手)、把大文件塞库、慢操作卡在请求主链路——均应外置 / 异步 / 批量化。
- 只认证不授权:每次访问都要校验「这个用户能碰这条记录吗」,别只在登录时把关。

**演进与触发信号**
- MVP:单体 + 一库,划清模块边界。成长:按需加 CDN / 缓存 / 读副本 / 队列,守无状态,哪疼治哪。成熟:组织真撑不住时沿清晰边界拆服务、分片。升级信号:出现具体瓶颈证据(读成瓶颈、慢操作、团队并行受阻)才升级,而非预判。

### 移动应用:离线优先的同步型客户端 (`mobile-app`)
**关键决策**
- 在线优先 vs 离线优先:交互频繁 / 弱网场景选离线优先(本地先写、UI 先动),代价是承担同步与冲突全部复杂度。
- 同步策略:全量 vs 增量 vs 双向——成熟应用标配「增量 + 双向」,同步引擎是最难写对、最藏 bug 的地方。
- 冲突解决:后写赢(简单但会丢改动) vs 版本向量 / CRDT(自动合并但门槛高),按数据重要性分级,真冲突抛给用户。
- API 版本:必须永远向后兼容(铁律),因无法强制升级,破坏性变更 = 主动让老客户端崩。

**常见反模式**
- 当瘦客户端每步同步请求;不做乐观更新转圈等;API 想改就改假设都升级;敏感数据明文存本地;每次拉全量;把易变业务规则(风控 / 定价)硬编进客户端。

**演进与触发信号**
- MVP:在线优先薄客户端,先验证需求。成长:本地缓存 + 乐观更新 + 单向同步 + BFF / 推送。成熟:完整离线优先 + 双向增量同步 + 分级冲突解决 + 版本治理。升级信号:出现「点了没反应」卡点、弱网体验差、多设备协作需求。

### 浏览器扩展:最小权限的注入型客户端 (`browser-extension`)
**关键决策**
- 逻辑放内容脚本 vs 后台 / 后端:内容脚本越薄越好(只碰 DOM),业务「大脑」上移,因内容脚本随刷新销毁、暴露在敌意环境、迭代慢。
- 权限:大权限(省事) vs 最小按需渐进申请——最小权限是立身之本,每项权限都在透支信任、放大风险面。
- 客户端 vs 后端:沿「隐私敏感度」切,敏感数据留本地只传最小片段。
- 商家适配规则:硬编码(只能发版修) vs 后端可下发(改配置即修),规模化后必须下发,但只下发配置 / 选择器而非可执行代码。
- 归因:必须选克制,归因劫持是法律与口碑双重地雷。

**常见反模式**
- 业务 / 密钥塞进内容脚本;申请「访问所有网站」;把「方便实现」凌驾于隐私之上;适配硬编码;下发可执行代码(远程注入后门);覆盖他人归因;注入 UI 喧宾夺主。

**演进与触发信号**
- MVP:薄内容脚本 + 后台 + 简单后端,手工维护券库,先验证佣金模型。成长:规则后端下发 + 数据采集管线 + 返现账本。成熟:联盟网络对接 + 众包闭环 + 隐私审计。升级信号:商家数上量(几十上百)、商家频繁改版拖垮发版修复。

### 短链服务:读路径优先的重定向系统 (`url-shortener`)
**关键决策**
- 短码生成:自增 ID→Base62(唯一但连续可枚举) vs 随机(不可枚举但需查重) vs 哈希取前(天然去重但撞码),多数选「自增 + 加盐打乱再 Base62」。
- 301 vs 302 ⭐:301 可被浏览器 / CDN 缓存(极快极省但收不到点击统计) vs 302 每次回源(统计完整但自扛流量)——要分析数据就用 302,精准体现「可缓存性 vs 可观测性」矛盾。
- 点击统计同步 vs 异步:必须异步,重定向是神圣快路,统计是旁路不能耦死。

**常见反模式**
- 同步写统计拖慢重定向;明文连续自增(可枚举可猜业务量);不做缓存每次打主存储;图省事用 301 丢掉所有分析;不校验目标 URL 沦为钓鱼帮凶;把它当复杂系统过度设计(难点只在读路径的快与稳)。

**演进与触发信号**
- MVP:单体 + 一库 + 自增转 Base62,同步统计也无妨(日点击 <10 万)。成长:读写拆开、加 KV 缓存、统计异步化、发号器换号段(百万~千万)。成熟:多区域多活、边缘 / CDN 重定向、映射表分片、独立实时分析管道(亿级)。升级信号:读路径出现瓶颈、缓存命中率待提升、全球延迟需求。

### 搜索引擎:倒排索引的两阶段检索系统 (`search-engine`)
**关键决策**
- 倒排索引 vs 顺序扫描 ⭐:必然选倒排,「拿写时(建索引)的代价换读时飞快」,代价是额外存储与更重的写入。
- 分片:按文档分(写简单易扩,但查询要 scatter-gather 扇出所有分片、受最慢分片拖累) vs 按词分(查询少但写入 / 热点词复杂)——绝大多数选按文档分。
- 召回 + 精排两阶段 ⭐:先轻量召回海量候选再重模型精排少量,「先粗后精」在推荐 / 风控通用。
- 索引新鲜度:全量重建 vs 近实时增量,多数场景近实时(秒~分钟级)足够,别为绝对实时过度付费。

**常见反模式**
- 用数据库 `LIKE '%x%'` 做全文搜索;索引时与查询时不分离互相拖累;一步到位对所有文档精排;追求 100% 实时索引;只堆技术不调相关性;企业搜索先搜后隐藏(权限过滤应在召回阶段介入)。

**演进与触发信号**
- MVP:直接用现成搜索引擎,单机 / 少节点,基础分词 + 关键词排序(百万级文档)。成长:分片 + 副本、近实时更新、自动补全 / 纠错、相关性初调(千万~亿级)。成熟:召回 + ML 精排(LTR)、查询理解、个性化、多语言、分布式大规模索引(十亿级)。升级信号:查询延迟、相关性不足、索引新鲜度需求上升。

### 社交信息流:推拉混合的时间线系统 (`social-feed`)
**关键决策**
- 推 vs 拉 vs 混合(命门):拉模型写轻读重(读放大严重) vs 推模型读轻但大 V 写扇出爆炸;规模化必然走混合——99% 普通用户走推、1% 大 V 走拉,代价是双路径合并复杂度上升。
- 大 V 爆炸破解:设粉丝数阈值,大 V 不扇出、由粉丝读时拉取合并,把「写时爆炸」转成「读时多一次合并」(读时有缓存可用)。
- 时间线存哪存多深:内存级 KV 只保留最近有限条,深翻走持久库降级路径。
- 排序:时间倒序(简单) vs 算法推荐(驱动商业指标但需信号 / 特征 / 模型管线),成熟期普遍转算法,且只对一小批候选(几百条)打分。
- 发文可见性:接受秒级最终一致,让扇出可异步 / 削峰 / 重试。

**常见反模式**
- 纯推不管大 V(扇出爆炸);纯拉扛高读 QPS(读放大);每次刷新为所有人实时重算全网排序(算力做不到);收件箱里存正文(应只存内容 ID);扇出同步卡住发文;可见性 / 拉黑只在前端隐藏;媒体从源站直发(应走 CDN)。

**演进与触发信号**
- MVP:拉模型 + 单库 + 时间倒序,先验证有人发有人看(几万用户)。成长:推模型 + 预计算时间线 + 多级缓存 + CDN + 扇出异步化(百万级),盯住第一批大 V。成熟:推拉混合 + 算法推荐(召回粗排精排) + 热点缓存 + 全球多区域 + 内容审核(千万~亿级)。升级信号:读侧瓶颈 / 刷新延迟、大 V 苗头出现。
